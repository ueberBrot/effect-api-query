# Contract-to-TanStack Query UX research

Research date: 2026-11-06. Registry metadata and sources checked around 15:55 UTC.

## Findings that affect prioritization

1. **The main opportunity is a shorter path through existing capabilities.** This adapter already exports options builders, tagged cache keys, inference helpers, declared-error lookup, scoped configuration, hydration codecs, stream snapshots, and recovery helpers. Its guides already cover optimistic writes and multiple frameworks. Treat recommendations below as proposals for discoverability or narrower conveniences, not a list of missing features. Sources: [README](../README.md), [public exports](../src/index.ts), [feature support](../apps/docs/src/content/docs/getting-started/feature-support.md).
2. **oRPC v2 is the closest API comparison, and is a published beta.** Its options-first API, accumulated/live views, scoped defaults, interceptors, and hydration helpers are real shipped capabilities in `2.0.0-beta.48`. Stable npm `latest` still points to `1.16.2`. Do not describe v2 as unreleased, stable, or the version obtained by an unqualified install. Sources: [registry tags][o-registry], [v2 migration guide][o-migrate], [published v2 package][o-tar], and the versioned sources cited below.
3. **Keep transport and server features in their proper layer.** tRPC batching and oRPC batching belong to their client links and server handlers. This project's application-owned transport is an explicit architectural decision. Publication batches into a Query cache are a different capability. Sources: [tRPC batch streaming][t-batch], [oRPC batch plugin][o-batch], [ADR 0026](../docs/adr/0026-keep-rpc-transport-aggregation-in-the-application.md).
4. **ts-rest is useful as a REST UX reference, with a maintenance caveat.** Its latest stable packages are v3, its React Query v5 integration is an import subpath, and its official site now announces that maintenance has ended and v4 will not ship. Sources: [core registry][s-registry], [React Query registry][s-query-registry], [maintenance notice][s-maintenance].

## Scope and evidence rules

This note compares tRPC's current `@trpc/tanstack-react-query` integration, oRPC v2's `@orpc/tanstack-query`, and ts-rest's `@ts-rest/react-query/v5`. The REST comparator contrasts generated options/key factories with wrapped hooks and caller-supplied keys.

Only official documentation, repository source, and publisher-supplied npm metadata/artifacts were used. Repository links pin competitor implementation evidence to release tags. Published oRPC JavaScript was inspected directly from its npm tarball to confirm exports, stream defaults, keys, and SSR behavior. API availability does not establish correctness under every framework or workload. No competitor application was built, no performance benchmark was run, and statements about absent helpers are limited to the reviewed adapter surface.

Local evidence is the working checkout, including changes already present when research began. This is a source/documentation comparison; it does not establish what the project's published npm artifact contains. The parent's example-coverage and dependency-range audits remain separate. No source, usage documentation, shipped skill, issue, branch, or PR was changed by this research.

## Verified capability comparison

### Options builders, inference, and operation choice

| Area | tRPC v11.25.0 | oRPC v2 beta.48 | ts-rest v3.52.1 |
| --- | --- | --- | --- |
| Normal reads/writes | A proxy provides `queryOptions(input, options)` and `mutationOptions(options)` for procedures declared as queries or mutations. Native TanStack hooks consume the results. [Query implementation][t-query-source], [mutation implementation][t-mutation-source]. | `createTanstackQueryUtils(client)` provides `queryOptions({ input, ... })`, `mutationOptions(...)`, and `.call` on client procedures. Options adapt a supplied client rather than constructing its transport. [Router source][o-router], [procedure source][o-procedure]. | `initTsrReactQuery(contract, clientOptions)` creates endpoint hooks and imperative helpers. Callers supply `queryData` and `queryKey`; hook wrappers internally construct the query function. There is no exported tRPC/oRPC-style options factory in the reviewed v5 construction surface. [Initialization][s-init], [hook implementation][s-hooks]. |
| Pagination | `infiniteQueryOptions` is exposed for query procedures accepting `cursor`; the adapter inserts page parameters into that convention. [Versioned usage][t-usage], [key/client argument source][t-utils]. | `infiniteOptions` accepts a page-parameter-to-input function and `initialPageParam`. Pagination need not use a field named `cursor`. [Types][o-types], [procedure source][o-procedure]. | Infinite hooks and imperative fetching use `queryData` as a function of Query's function context, so the application maps `pageParam` into request data. [Hook implementation][s-hooks], [hook option types][s-options]. |
| Type contract | Builder overloads carry input, output, selected data, initial-data behavior, and typed errors. Query keys use `DataTag`. [Query implementation][t-query-source]. | Utility types derive input, output, and errors from the supplied client. Query keys carry output/error tags; selection and initial-data cases are represented in the builder types. [Router types][o-router], [Query types][o-types]. | Contract types flow into request data, successful response envelopes, error envelopes, and endpoint-specific cache helpers. Cache typing is supplied by the endpoint wrapper around the caller's key. [Response types][s-types], [cache helper types][s-cache-types]. |

**Local comparison.** Unary RPC and buffered nonmultipart HTTP leaves already expose query, infinite, and mutation builders. The call site chooses the operation; infinite input is a page mapper. Concrete keys carry data/error tags, while `InferInput`, `InferQueryData`, `InferQueryError`, `InferMutationData`, and `InferMutationError` describe leaf contracts. Selection changes observer results without changing the cached-data type. RPC accepts payload constructor input, including omitted defaults; HTTP accepts decoded request containers. Sources: [README](../README.md), [inference implementation](../src/core/inference.ts), [type inference reference](../apps/docs/src/content/docs/reference/type-inference.md), [ADR 0002](../docs/adr/0002-let-call-sites-choose-query-or-mutation.md), [ADR 0018](../docs/adr/0018-add-infinite-query-builders-for-unary-rpcs.md).

**Inference.** This adapter is already in the options-first family. oRPC's object argument and generic page mapper are especially close. ts-rest demonstrates why generated typed keys are useful: its endpoint typing does not generate cache identity from request input. This is an API comparison, not evidence that any option style is universally easier.

### Errors and cache operations

| Area | tRPC v11.25.0 | oRPC v2 beta.48 | ts-rest v3.52.1 |
| --- | --- | --- | --- |
| Error narrowing | The client error type carries server error shapes. Current v11 supports both a root `errorFormatter` and per-procedure `.errors()` formatters producing unions of shapes. Handler order affects which failures a formatter sees. Calling this “global error formatting only” would be outdated. [Error formatting][t-errors], [procedure builder][t-procedure-builder]. | `safe` preserves the client's typed error result outside hooks; `isDefinedError` distinguishes defined errors from other thrown failures. Defined error codes and data come from the contract's error map. Query/mutation error types follow the client. [Client error guide][o-errors], [utility types][o-router]. | Error types include declared non-2xx responses, undeclared response bodies typed as unknown, and ordinary `Error`. `isFetchError` and `isNotKnownResponseError` help separate those cases before narrowing on HTTP status. [Response types][s-types], [guards][s-guards]. |
| Cache identity and invalidation | `queryKey`, `infiniteQueryKey`, `queryFilter`, and router `pathFilter` support native QueryClient operations. Keys identify path, input, and query kind. Key prefixing is available behind the integration's `keyPrefix` feature flag; it is not automatic per-client isolation. [Versioned usage][t-usage], [key source][t-utils]. | `.key()` supports broad or typed/input partial matching; concrete view keys support exact cache access. Keys contain an optional prefix, procedure path, and operation/input information. Client context is excluded. The default key serializer distinguishes supported rich values by their serialized type metadata. [Key source][o-key], [shared key interface][o-shared], [procedure source][o-procedure]. | The application chooses keys and keeps them aligned with request data. Endpoint-scoped `getQueryData`/`setQueryData` provide typing; `invalidateQueries` remains the native root QueryClient method. [Hook/cache construction][s-hooks], [v5 docs][s-query]. |

**Local comparison.** The adapter already preserves failed Effect `Exit`s in an execution error with the full `Cause`. `findDeclaredError(error, tag)` returns a typed `Option` only for a single matching typed failure; defects, interruptions, composite Causes, and non-wrapper errors remain outside that convenience match. It does not flatten the original wrapper or promise to classify arbitrary callback/runner rejections. Sources: [declared-error implementation](../src/core/declared-error.ts), [failure guide](../apps/docs/src/content/docs/guides/handle-failures.md), [ADR 0005](../docs/adr/0005-preserve-the-cause-in-one-error-wrapper.md).

Local keys already have explicit non-empty safe prefixes, separate RPC/HTTP roots, view identity, and canonical payloads. Native prefix invalidation, `viewPrefix`, `createQueryFilter`, and `createBranchQueryFilter` cover exact, leaf-view, and branch-view workflows. Partial filters intentionally require explicit projections: running a full constructor would introduce defaults and overconstrain matches, while custom encoders cannot generally be inverted. Sources: [semantic key guide](../apps/docs/src/content/docs/concepts/semantic-keys.md), [cache filters](../apps/docs/src/content/docs/guides/cache-filters.md), [ADR 0008](../docs/adr/0008-use-flat-prefix-matchable-key-tuples.md), [ADR 0028](../docs/adr/0028-bind-partial-filters-to-explicit-projections.md).

**Inference.** oRPC makes partial matching more directly discoverable on the utility tree. The local separation is justified by constructor normalization and encoder semantics. Any attached filter convenience should delegate to the existing projection contract. Cache namespaces must still include safe owner identity when returned data depends on it; a client instance or hidden context is not automatically a cache namespace.

### Streaming, batching, and SSR

| Area | tRPC v11.25.0 | oRPC v2 beta.48 | ts-rest v3.52.1 |
| --- | --- | --- | --- |
| Cached streaming | A query returning an async iterable is detected by `queryOptions`; its values are accumulated into an array in the cache. The reviewed accumulation helper resets to an empty array and grows it per emission; it exposes no retention or latest-only argument. Separately, subscription procedures use `subscriptionOptions` and tRPC's own `useSubscription`. [Query implementation][t-query-source], [accumulation source][t-utils], [subscription source][t-subscription]. | `streamedOptions` accumulates events with `reset`, `append`, or `replace` refetch policies and optional `maxChunks`; the shipped default retention is infinity. `liveOptions` replaces the cached value and errors if completion precedes any event. [Accumulation source][o-stream], [live source][o-live]. | The stock fetcher awaits JSON, text, or Blob buffering. The reviewed v5 adapter has no accumulated/live builder. Custom fetchers can change request execution, but that does not establish a built-in streaming cache policy. [Default fetcher][s-fetch], [hook construction][s-hooks]. |
| SSE and NDJSON | `httpSubscriptionLink` supplies SSE subscriptions. `httpBatchStreamLink` supplies tRPC's JSONL batch protocol, including streamed iterable results. Its framing is not a general-purpose adapter for an arbitrary REST NDJSON endpoint. Server and link configuration determine the protocol. [SSE link][t-sse], [batch stream link][t-batch]. | oRPC's async-iterator protocol provides SSE event metadata and completion semantics; client iteration can stop through a signal or `.return()`. Bare iterator consumption does not automatically retry; retry/resume support belongs to the client/plugin/server stack. The reviewed Query adapter consumes iterators, not raw NDJSON framing. [Protocol guide][o-iterator-protocol], [client iterator guide][o-iterator], [procedure source][o-procedure]. | Buffered HTTP response decoding in the stock fetcher is not a generic SSE/NDJSON event decoder. This statement concerns the reviewed stock client/Query path, not every possible custom fetcher or server. [Default fetcher][s-fetch]. |
| Request batching | `httpBatchLink`/`httpBatchStreamLink` combine transport operations. Streaming responses can arrive independently, but each server resolver still runs; database batching is a separate data-layer concern. [Batch stream link][t-batch]. | A `BatchLinkPlugin` and `BatchHandlerPlugin` cooperate to aggregate outgoing/incoming requests. This is link/handler infrastructure, not a feature introduced by `queryOptions`. [Batch plugin][o-batch]. | The reviewed hook wrapper invokes its configured fetcher per query. Parallel Query hooks do not by themselves imply request aggregation. No automatic batching claim is justified by this adapter implementation. [Hook source][s-hooks]. |
| Hydration | Official RSC/Start recipes use request-local QueryClients, native dehydration/hydration, matching data transformers, and client/server-specific execution. Start uses TanStack's SSR Query integration; tRPC does not supply a separate router integration. New `unstable_$` handles coordinate prefetch/ensure and later reads; they are explicitly unstable APIs. [RSC recipe][t-rsc], [Start recipe][t-start], [handles source][t-handles]. | `createHydrationOptions(serializer)` pairs serialization/deserialization callbacks. `StreamQuerySSRUtilsPlugin` cancels server stream queries on a success publication and forces browser refetch on mount. Accumulated streams publish an empty cache when connected, so cancellation need not wait for their first event; live queries wait for a value. This is not the same capture contract as the local helper. [SSR implementation][o-ssr], [stream implementation][o-stream]. | SSR uses an application-created QueryClient passed to `initQueryClient`, then prefetch plus native dehydration/hydration. The reviewed initialization surface does not install a general rich-value serializer or a stream snapshot helper. [Initialization][s-init], [official SSR section][s-query]. |

**Local comparison.** RPC streams and eligible HTTP SSE/NDJSON endpoints already have separate accumulated streamed query and live query views. Retention must be a finite positive `maxChunks` or an explicit `"unbounded"` choice, including inherited configuration. Refetch/retention/publication policies participate in accumulated cache identity. Publications can batch by count/deadline; these batches do not aggregate network requests. The first emission remains immediately visible. Sources: [stream guide](../apps/docs/src/content/docs/guides/streaming.md), [ADR 0020](../docs/adr/0020-generate-accumulated-and-live-stream-queries.md), [ADR 0031](../docs/adr/0031-add-explicit-query-reuse-and-stream-controls.md), [ADR 0032](../docs/adr/0032-configure-utility-trees-and-require-stream-retention.md).

The ready Effect HTTP API client owns NDJSON framing/Schema decoding and declaration limits; the adapter projects decoded records into cache views. It omits raw byte streams, upgrades, streaming request bodies, and ambiguous mixed success representations. This distinction is essential when comparing a thin adapter with complete RPC/REST stacks. Sources: [feature support](../apps/docs/src/content/docs/getting-started/feature-support.md), [ADR 0024](../docs/adr/0024-project-http-streams-and-buffered-metadata.md), [ADR 0034](../docs/adr/0034-extend-http-stream-views-to-decoded-ndjson.md).

For SSR, local `fetchStreamSnapshot` captures a first new publication or completion, cancels its exclusively owned exact query, and awaits local iterator cleanup. It supports explicit cached reuse. The application then serializes/dehydrates and releases request resources; the browser owns independent resources. `queryViewCodec`, `infiniteQueryCodec`, `hydrationCallbacks`, and `createHydrationRegistry` preserve explicitly selected cached representations. The registry rejects unsettled entries and unregistered views; it is not universal serialization of every query or arbitrary pending promise. Sources: [snapshot guide](../apps/docs/src/content/docs/guides/stream-snapshots.md), [hydration source](../src/core/hydration.ts), [public exports](../src/index.ts).

**Inference.** Stream retention and capture cleanup are strengths to explain, not missing parity. oRPC offers fewer application wiring steps through its serializer helper and SSR plugin. Local explicit capture has different ownership and cleanup guarantees. A convenience wrapper must preserve them. Neither implementation's browser reconnect establishes lossless delivery or server replay by itself.

### Optimistic mutation UX, configuration, and lifecycle

| Area | tRPC v11.25.0 | oRPC v2 beta.48 | ts-rest v3.52.1 |
| --- | --- | --- | --- |
| Optimistic writes | Mutation options retain TanStack callback and optimistic-context typing and expose native mutation keys. The reviewed builder does not derive affected reads or supply a domain rollback algorithm. [Mutation source][t-mutation-source]. | Mutation option types retain native optimistic context. Scoped callbacks/interceptors can invalidate a selected branch. Domain-specific cache edits and rollback remain application logic in the reviewed implementation. [Types][o-types], [procedure implementation][o-procedure]. | Official docs show a complete optimistic list edit, saved snapshot, rollback on error, and invalidation on settlement using typed endpoint cache helpers. That recipe does not demonstrate coordination of overlapping writes. [Complete example][s-query]. |
| Shared behavior | Mutation options integrate QueryClient defaults and an optional success override. These are reusable policy mechanisms, not automatic dependency tracking between mutations and queries. [Mutation source][t-mutation-source]. | `scoped` supplies typed leaf defaults; modifier functions can customize merging. Interceptors wrap execution. `tanstackQuery` plus `ContractOptionsUtilsPlugin` can put defaults/interceptors in contract metadata. These ship in the inspected v2 beta. [Router source][o-router], [procedure source][o-procedure], [metadata plugin source][o-meta]. | Client setup combines contract and HTTP options; the adapter exposes native options through wrapped hooks and extends the supplied QueryClient. [Initialization][s-init], [hook implementation][s-hooks]. |
| Setup/lifetime | React context setup uses a tRPC provider and Query provider. A documented `createTRPCOptionsProxy` alternative avoids tRPC context. New clients/QueryClients are request-local for SSR. The query builder forwards the abort signal when `abortOnUnmount` is enabled. [Setup][t-setup], [query source][t-query-source]. | Utilities take an existing client. The Query integration requires no oRPC-specific React provider and uses Query Core types; framework providers/reactivity remain native. Its query execution forwards Query's signal to the client. Transport construction remains in the client/link stack. [Router source][o-router], [procedure source][o-procedure], [types][o-types]. | Initialization accepts `baseUrl`, headers, and a custom fetcher through client options. The documented provider sits inside QueryClientProvider; SSR can initialize the typed client imperatively. [Initialization][s-init], [v5 setup][s-query]. |

**Local comparison.** `configureUtils` already supplies tree/branch/leaf policies and ordered interceptors. Mutation callbacks replace by default or explicitly compose shared-before-local; optimistic `onMutate` context remains local. Existing optimistic-write guidance goes beyond a whole-list snapshot: it documents mutation-response seeding, infinite page preservation, per-write rollback, overlapping settlements, and original-owner retention. This is documented application workflow, not a generic library transaction engine. Sources: [defaults/policies](../apps/docs/src/content/docs/guides/query-defaults.md), [optimistic writes](../apps/docs/src/content/docs/guides/optimistic-writes.md), [ADR 0027](../docs/adr/0027-opt-in-policy-composition-and-execution-interceptors.md), [ADR 0032](../docs/adr/0032-configure-utility-trees-and-require-stream-retention.md).

The factories take ready clients and do not acquire/dispose them. Queries forward cancellation; mutations have no query abort signal. Stopping consumers, settling local cleanup/accepted mutations, clearing the cache, and releasing resources remain application responsibilities. Sources: [client lifecycle](../apps/docs/src/content/docs/concepts/client-lifecycle.md), [ADR 0007](../docs/adr/0007-keep-the-core-factory-lifecycle-neutral.md). A correct optimistic cache rollback does not undo an accepted server mutation.

### Framework support and rich decoded values

| Area | Verified competitor behavior | Local comparison |
| --- | --- | --- |
| Framework surface | tRPC's reviewed options package imports React Query and ships React context/subscription APIs; the source does not establish a universal first-party Vue/Solid/Svelte/Angular options adapter. [Package metadata][t-query-registry], [query source][t-query-source]. oRPC v2 uses Query Core and includes release-tagged type fixtures for React, Vue, Solid, Svelte, and Angular. This verifies intended type integration, not every framework build/runtime. [Types][o-types], [framework fixtures][o-frameworks]. ts-rest's reviewed v5 entry point imports React; its website also lists a separate Vue Query v4 integration, which is not Vue Query v5 certification. [Initialization][s-init], [official client navigation][s-query]. | The project has native React, Vue, Solid, Svelte, and Angular guidance and TypeScript consumer checks. The compatibility reference distinguishes those checks from component compilers and app builds; retain that distinction. [Integration index](../apps/docs/src/content/docs/integrations/index.md), [compatibility reference](../apps/docs/src/content/docs/reference/compatibility-and-limits.md), [ADR 0004](../docs/adr/0004-build-core-shaped-options-and-certify-react-first.md). |
| Structural sharing | oRPC v2 installs rich-value structural sharing for ordinary/live/infinite options, with handling for `Date`, `URL`, `Map`, and `Set` and serializer-aware custom values. It can be overridden per call. [Procedure source][o-procedure], [sharing implementation][o-sharing]. | Local builders retain native Query behavior. An existing opt-in guide uses Schema equivalence and native sharing for an explicitly modeled decoded shape. No universal rich-value helper is exported. [Sharing guide](../apps/docs/src/content/docs/guides/share-decoded-values.md), [public exports](../src/index.ts). |

**Inference.** oRPC's default sharing can reduce setup for immutable rich values, but that does not prove lower total cost. Automatic equality for arbitrary Effect Schema classes, extra instance state, mutable values, or lossy codecs requires a separate design argument and measurement. Framework compatibility claims should name their evidence level rather than imply all integrations have complete running example applications.

## Proposed improvements, in priority order

These are research recommendations, not implemented changes or verified usability study results. Existing guides are linked so the parent can assess what is already surfaced in the examples audit.

| Priority | Proposal | Evidence and constraint |
| --- | --- | --- |
| P0 | Use a dated, layer-aware comparison when positioning the library. Say “oRPC v2 beta” and “ts-rest v3,” and distinguish Query options from links, server adapters, replay, and authentication. | The version/ownership findings above prevent false gaps. Preserve [ADR 0007](../docs/adr/0007-keep-the-core-factory-lifecycle-neutral.md), [ADR 0026](../docs/adr/0026-keep-rpc-transport-aggregation-in-the-application.md), and [ADR 0034](../docs/adr/0034-extend-http-stream-views-to-decoded-ndjson.md). |
| P1 | Make the smallest complete read/write workflow easier to find: acquire one owner, build options, render a read, perform a write, seed a concrete key, then invalidate its branch. Link immediately to error narrowing, pagination, and owner replacement. | Competitor setup/API pages colocate these tasks. Local [quick start](../apps/docs/src/content/docs/getting-started/quick-start.md), [HTTP quick start](../apps/docs/src/content/docs/getting-started/http-quick-start.md), [optimistic writes](../apps/docs/src/content/docs/guides/optimistic-writes.md), and [integrations](../apps/docs/src/content/docs/integrations/index.md) already contain the ingredients. Assess navigation/example prominence before adding APIs. |
| P1 | Present two SSR decisions together: how cached values survive serialization, and how open streams settle before disposal. Offer a short decision path for plain DTOs, Schema classes, infinite pages, and first-event snapshots. | oRPC packages serializer callbacks and stream SSR setup; local codecs/snapshots already support explicit policies. Reuse [snapshot guidance](../apps/docs/src/content/docs/guides/stream-snapshots.md) and [hydration helpers](../src/core/hydration.ts). Any convenience must retain exclusive capture, finalizer settlement, independent browser ownership, and explicit codec coverage. |
| P1 | Surface the shortest declared-error branch alongside a mutation example, with an explicit fallback for other failures. | All reviewed competitors have a direct narrowing path. Local `findDeclaredError` already supplies it. Promote [Handle Failures](../apps/docs/src/content/docs/guides/handle-failures.md); do not replace the complete Cause with a flattened union or claim all thrown values match inferred errors. |
| P1 | Keep optimistic mutation teaching in two stages: a simple single-write workflow, followed by the existing overlapping-write/owner-retirement workflow. Make pending, failure, rollback, and final reconciliation visible in any UI demonstration. | ts-rest's compact example is approachable; local [optimistic writes](../apps/docs/src/content/docs/guides/optimistic-writes.md) addresses more failure cases. This is a discoverability proposal, not a claim that the current examples lack those states. Avoid a universal rollback API without a domain model for conflicts. |
| P2 | Consider an optional rich-value sharing convenience only after measuring real decoded shapes and consumer benefits. | oRPC supplies this by default. Local [schema-defined sharing](../apps/docs/src/content/docs/guides/share-decoded-values.md) is already an opt-in solution. Preserve explicit decoded equality and arbitrary-class semantics; serializer equality alone is insufficient evidence. |
| P2 | Evaluate whether filter construction needs a more discoverable leaf/branch entry point. | oRPC's `.key({ type, input })` and tRPC's filters are easy to discover. Existing local helpers already work. Any shortcut must preserve [ADR 0028](../docs/adr/0028-bind-partial-filters-to-explicit-projections.md), view discrimination, and heterogeneous bulk-result typing. |
| P2 | If setup remains a measured pain point, extract an application-owned owner/provider template before adding lifecycle to the package. | Competitor setup bundles more stack decisions. Local ownership is deliberate. A template can choose transport, Scope, runner, QueryClient, and teardown without changing the core factories. Reuse [Client Lifecycle](../apps/docs/src/content/docs/concepts/client-lifecycle.md). |

No evidence here justifies automatic transport batching inside this adapter, automatic mutation-to-read dependency discovery, an adapter-owned server, or an implicit promise of resumable/lossless streams. Those would change scope and require separate design decisions. The reviewed features establish API choices, not a measured ranking of developer productivity, runtime performance, bundle size, or compile speed.
